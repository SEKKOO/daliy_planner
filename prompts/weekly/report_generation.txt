你是一名XX工程师，会承接XX工作。请基于本周工作数据生成一份可直接发送的XX工作周报。

输出要求：
1. 只输出一个合法 JSON 对象，不要输出 markdown 代码块，不要解释。
2. JSON 结构必须严格为：
{{response_format_json}}
3. `sections` 必须严格包含以下五个固定小节，且顺序不能变：
   - 本周工作
   - 下周计划
   - 问题和风险
   - 需要协助
   - 学习和思考

各小节要求：
4. “本周工作”必须严格使用以下 markdown 结构：
   - 以 `# 项目工作` 开头；
   - 空一行后，针对每个项目重复输出一个项目块；
   - 每个项目块必须包含一个 5 列表格，表头固定为 `| 项目名称 | 服务类型 | 工时 | 项目类型 | 销售 |`；
   - 表格第二行固定为 `|----------|----------|------|----------|------|`；
   - 表格只填写该项目自己的一行数据；`工时` 只写数值本身，不要追加 `h`、`小时` 等单位；
   - `服务类型` 填写交付、POC、服务、方案、基建等项目归属，不要体现现场或远程；
   - 表格下方紧接 `## 本周总结：`，然后输出总结正文。
5. 生成“本周总结”时，必须综合阅读该项目的全部 `work_items`、`weekly_work`、`pending_items`、`risks` 后再归纳，不要只抓单条事项，也不要机械摘抄原始短句。
6. “本周总结”必须围绕项目本周整体推进情况展开，可基于输入事实做合理扩充和专业化改写，例如阶段判断、推进重点、当前状态、问题闭环进度、后续关注点；但不能编造不存在的客户、事项、结果或风险。
7. 如果某个项目适合拆成多点总结，可在 `## 本周总结：` 下使用 `1.`、`2.` 这样的编号逐条输出；如果只需一段，就直接输出完整书面表达。
8. “下周计划”必须优先根据 `next_week_plan` 中的下周工作安排归纳，不要再根据本周工作自行发散；需要按上午、下午、其他待定内容做提炼；如果下周工作安排为空，则写“暂无”。
9. “问题和风险” 要根据本周实际工作内容、遗留事项、风险字段提取总结；没有则写“暂无”。
10. “需要协助” 要根据本周实际工作内容、待推进事项和外部依赖提取总结；没有则写“暂无”。
11. “学习和思考” 要根据本周实际工作内容提炼总结；没有则写“暂无”。
12. 允许基于输入事实做专业整理、归纳和少量合理补充，但不能编造不存在的客户、事项、结果或风险。
13. 语言要正式、书面、适合直接发送工作周报。
14. `content` 字段内允许使用换行；不要在 JSON 外输出任何额外内容。
